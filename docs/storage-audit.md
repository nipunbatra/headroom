# Headroom storage and usability audit

26 November 2026 · Baseline `906e1b4` · Native macOS app, scanner, cleaner, CLI and release scripts

The highest-risk findings were in the transition from discovery to deletion. A filtered list could stage hidden items. The default safe set could empty the Trash. The confirmation button could run before its preview arrived. All three paths now have app-model or engine regression coverage. The revised overview gives a first-time user four specific places to look and opens the corresponding filtered list with one click.

## Findings and changes

| Priority | What the audit found | Change and evidence |
| --- | --- | --- |
| High | Quick cleanup treated Trash as safe. The Finder command could empty Trash across volumes while Headroom measured the home Trash. | The current rule explicitly reviews the contents of the home Trash. Old saved scans adopt the current rule on load. Tests exercise migration, fixture-only removal and the fresh review offered after a cleanup. |
| High | Download, project, duplicate and rule bulk buttons computed their targets before applying filters. Keyboard selection could also outlive the visible row. | Bulk actions use the visible eligible rows. Duplicate selection is individual. List changes reconcile keyboard selection. Tests cover category, filename, age, project type and empty results. |
| High | Return could confirm an unfinished preview. Changing the deletion mode or removing a row could allow an earlier asynchronous result to replace the latest one. | Confirmation requires the finished preview for this revision and deletion mode. Running a session retains the approved targets. Tests cover immediate confirmation, rapid mode changes, removing a row, a fully refused session and successful Trash execution. |
| High | Resolving the same ID again could silently add targets or act on a replacement file. Overlapping parent and child actions could run twice. | Path-based work checks the target list and revalidates each item immediately before its turn. Permanent directory operations fingerprint descendant metadata and use descriptor-relative removal with mount crossing disabled. Conflicting selections identify each other in the sheet. Fixtures cover replacements, new children at two depths, and overlap resolution. |
| High | Shared samples could describe two different files as duplicates. The retained copy could change or disappear between the scan and cleanup. Clone copies were assigned the group’s allocated size. | File size and content samples shortlist candidates. A bounded full SHA-256 pass confirms groups. Each duplicate action compares the selected and retained files in full during review and again at execution. The sheet catches a separately selected retained copy. Each copy carries its own reclaim estimate. |
| High | A file named like a build directory, or an ordinary folder named `target` or `Pods`, could qualify for permanent removal. The generic file route could also bypass the uninstaller’s checks. | Permanent build cleanup requires a directory and the scanner’s classification. Cargo and CocoaPods require their project markers. Installed bundles use the uninstaller. If moving the bundle fails, its support data stays in place. |
| High | An incomplete Hugging Face reference inventory could make a still-needed blob appear unused. | Blob cleanup now requires readable, local directories and resolvable references. A fixture with an incomplete model index retains the blob. |
| High | A home-wide bytecode command covered more than the reported projects. Old temp directories could contain active descendants. Docker’s active context could be remote. | These aggregate operations now direct the user to individual review or the owning tool. Maven artifacts and notebook checkpoints also require review because they can hold local-only work. |
| Medium | A missing project activity date qualified as idle. Download age could read like last access. The overview mixed overlapping opportunities and implied a predictable amount of free space after cleanup. | Unknown activity stays out of idle builds. Downloads explicitly use modification dates. The overview links to independent review sets. The sheet distinguishes estimates, Trash and tool-managed cleanup. |
| Medium | One unsupported filesystem could disable fast reads process-wide. A live folder listing could double-count hard links and report unreadable subtrees as complete. | Bulk-read fallback is local to a read. Live listings count hard-linked bytes once, check the volume boundary and mark incomplete measurements. Shared-space credit requires a known matching clone count. |
| Medium | An invalid CLI root could silently start a whole-disk scan. Cancellation during report building could publish an unwanted replacement. | Invalid roots and worker counts return an error. Late cancellation is checked before publishing. The report is written before scan history. Tests check invalid CLI arguments, preservation of prior data, and history timestamps. |
| Medium | The old self-test accepted a naming convention in a path in the real home. Release builds could silently fall back to a single architecture. | Developer cleanup requires an explicit temporary fixture home, file IDs and a fixture-local Trash. A release build requires both architectures. Temporary build and test products are staged and cleaned. |

## Storage workflows

| User goal | Entry point in this build | What the user can verify |
| --- | --- | --- |
| Find a few large opportunities | Overview → Where to start | Installers, older downloads, idle builds and duplicate groups open as filtered lists. An installer can also be an old download, so the four amounts should be read independently. |
| Keep a tool cache between scans | Settings → Quick Cleanup, or the rule’s context menu | Exclusions survive relaunch. If an excluded cache is later bundled into a smaller-cache group, that group is withheld from Quick Cleanup. Explicit selection is still available. |
| Decide whether two files are interchangeable | Large Files → Duplicate groups | See the paths, the retained copy and whether the scan sampled or fully matched the contents. Quick Look and Reveal in Finder remain available. |
| Understand exactly what a cleanup does | Cleanup List → Review and Clean | Expand an entry to inspect its paths or command. Each entry reports its removal method or refusal. The confirmation count includes runnable items. |
| Understand missing space | Overview → Notes from the Scan | Expand the folders macOS declined to open. The list shows the recorded paths and offers access settings when appropriate. |
| Explore an unfamiliar folder | Disk Map | A folder tile with children drills down. A single-file tile opens Quick Look. The accompanying list provides a keyboard-accessible route. |

## 0.4.0 release audit

The biggest gaps for someone deciding what to delete were control over app data, finding a particular file inside a group, and narrowing a long list by size and age. The first public release addresses all three. Competitor capabilities below come from published product guides. Headroom observations come from the Swift sources, fixture tests, and the running app.

| Workflow | Headroom 0.4.0 | Gap and priority |
| --- | --- | --- |
| Uninstall an app and preserve its data | The bundle starts selected. Profiles, preferences, caches, and other matched Library paths start unchecked. Each choice changes the estimate and triggers a live preview. The engine refuses a path that no longer belongs to that app. | **High.** There is no inventory of leftovers from previously removed apps, or a guided retry after a partial uninstall. A future orphan inventory needs evidence of ownership and a Finder preview for each path. [Mole uninstall](https://github.com/tw93/Mole#uninstall) · [CleanMyMac applications](https://macpaw.com/support/cleanmymac/knowledgebase/uninstaller) |
| Keep a project or folder out of cleanup | Quick Cleanup remembers excluded rules. Permanent build-folder cleanup refuses nested Git repositories and worktrees. Explicit review can still select paths excluded from Quick Cleanup. | **High.** Add protected paths enforced by the engine across previews, batches and external tools. Include build outputs tracked by an enclosing repository in acceptance tests. [Mole cleanup and project purge](https://github.com/tw93/Mole) · [CleanMyMac ignore lists](https://macpaw.com/support/cleanmymac/knowledgebase/ignore-lists) |
| Explore an external disk or one folder | The CLI takes a folder root. The SwiftUI scan button uses the startup disk. Tree walks stay within a volume. | **High.** Add a read-only volume or folder picker and key history, free-space figures, exclusions and saved selections by volume identity. Verify unplugging a drive mid-scan and reconnecting another with the same name. [Space Lens](https://macpaw.com/support/cleanmymac/knowledgebase/space-lens) · [Mole analyzer](https://github.com/tw93/Mole#analyze) |
| Find one large, old file | Combine 1 GB or 5 GB size thresholds with 90-day or one-year modification thresholds, kind, and search. Filtering uses allocated size even when the recoverable estimate is smaller. Search also finds nested cache entries and app components in the report. | **Medium.** CleanMyMac also groups by last access. Headroom has modification time for large files. The report keeps the top 400 eligible large files and the list displays up to 300 matching rows. A complete searchable inventory would require pagination and different report limits. [MacPaw large and old files](https://macpaw.com/support/cleanmymac/knowledgebase/large-and-old) |
| Review what a cleanup changed | Local action log, free-space chart, and folder growth since the last scan. Duplicate totals now update after a copy is cleaned. | **Medium.** Add a per-session history view with individual outcomes, removal method and retryable paths. Distinguish estimated bytes from space observed later. [Mole history](https://github.com/tw93/Mole) |
| Find redundant photos and cloud content | Duplicate groups shortlist large files by content sample and verify copies during removal. The scanner skips cloud placeholders to avoid triggering downloads. | **Lower.** Similar-image discovery, small-file duplicate coverage, and cloud-provider review would need separate matching and local-availability models. Similar images should require visual comparison. [CleanMyMac feature matrix](https://macpaw.com/support/cleanmymac/knowledgebase/missing-features) |
| Manage updates, background items and system health | Headroom provides storage measurement, change history, a menu bar indicator and low-space alerts. | **Adjacent scope.** Application updating, malware scanning, login-item management, and CPU/SMART monitoring are separate products or operating-system integrations. They rank below storage review and recovery. [CleanMyMac tools](https://macpaw.com/support/cleanmymac/knowledgebase/my-tools) · [Mole status](https://github.com/tw93/Mole#status) |

### Release regressions fixed

- A failed model-repository removal could still delete its backing blobs. A fixture changes the repository after review and verifies that both the repository and its blob survive.
- The scan output path could collide with the history file or action log. The writer now rejects those reserved filenames before the walk, including case variants.
- A scoped Applications scan could report unrelated apps and Library paths. Both scanner implementations now restrict the inventory to the requested root. Shared bundle identity checks still look across installed apps.
- Cleaning a duplicate copy left a stale group count and byte estimate. Overview and Large Files now use the same remaining copies. If the designated keeper is removed separately, the group drops out until another scan.
- The tests also cover bundle-only removal, mixed app/support selection conflicts, opting a path in and back out, a forged support path or one whose bundle identifier becomes shared, unknown file dates, inclusive size and age boundaries, and selecting a search match without staging its parent.

## Verification

The original suite passed **39 tests and 267 checks**. The first audit pass reached **71 tests and 392 checks**, including a Thread Sanitizer run on Apple silicon. Release 0.4.0 passes **78 tests and 433 checks**, including a second run of the complete Swift suite under Thread Sanitizer. A native accessibility check selected both new Large Files filters and confirmed that six example files narrowed to three. The independent Python cross-check compares a shared 37-file fixture across seven rules, four project folders, eight large files and two duplicate groups. Separate Swift fixtures cover deliberate changes from the reference implementation.

Destructive tests use temporary files, an isolated preferences suite where persistence matters, and a fixture-local Trash. The native window checks use a synthetic file inventory. An Accessibility API check pressed the Installers shortcut, observed the single matching row, added it to the inspector, opened the review sheet, observed the missing-file refusal, and cancelled. A second run at the 880-point minimum window width used an existing fixture file, reached its single-item Trash preview and cancelled with the file intact. All eight main pages, the inspector, sheet, settings and menu panel were captured in light and dark appearances. The machine runs macOS 15.7.7 with the Swift 5.9 command-line toolchain. Both architectures target macOS 14. The release and its extracted zip passed signature verification. The packaged CLI scanned an isolated folder using the arm64 slice and the x86_64 slice through Rosetta. An invalid root returned status 2 and preserved the existing report. The packaged GUI’s self-test reviewed a file, moved it into the fixture’s Trash, and preserved its contents.

**Performance measurement.** An optimized before-and-after run used the reference fixture plus 12,000 small source files, giving 12,037 files and two duplicate groups. Five warm measurements alternated the order of the two binaries after one warmup each. Median scan and report time was **0.024 seconds before and 0.393 seconds after**. The new scan does more I/O to confirm full-file matches. This benchmark used a warm filesystem cache and a small synthetic tree. A fresh full-disk timing is still needed.

## Remaining work, in priority order

1. **Bound external cleanup tools.** A package manager chooses its targets from its own configuration. The sheet shows the command, but cannot enumerate its effects. The subprocess runner buffers combined output and requests termination at its deadline. A child holding the output pipe open can delay completion. Add per-tool scope checks, bounded output and a process-tree timeout test before enabling more commands.
2. **Improve recovery from partial batches.** If an app bundle moves successfully and a later support path fails, the action log records the error. Re-running the app action now sees a missing bundle. Retaining the exact remaining paths in the result would allow a focused retry. Recursive filesystem changes during the final operation are also possible after revalidation, and concurrent processes do not share the in-process cleanup lock.
3. **Refine estimates on difficult filesystems.** Full scans still attribute a hard-linked file to the first folder a worker reaches. Sparse files, shared APFS blocks, snapshots, commands that prune only part of a cache and unrelated writes affect the difference between a displayed estimate and a later volume reading. Next test a matrix of APFS clones, hard links spanning scan roots, cloud providers and external filesystems on separate volumes.
4. **Measure cancellation latency and large-volume performance.** Duplicate hashing checks cancellation in chunks. Some other report-building work must finish before cancellation takes effect. Permanent recursive review also incurs a metadata walk. Measure peak memory, cancellation latency and preview time on a multi-million-file volume before publishing a new full-disk speed claim.
5. **Extend navigation and accessibility testing.** Nested rule and app components are searchable. The Overview search still omits map-only folders and scan-change rows. Add VoiceOver walkthroughs, larger text, compact layouts across the remaining pages and Intel/macOS 14 hardware checks. The current native captures give visual coverage on one machine.
6. **Separate future product work from release qualification.** The public ZIP is Developer ID signed with hardened runtime and a secure timestamp. Notarization and a fresh-machine Gatekeeper installation remain open. The legacy Python server and HTML viewer remain separate from the native app and its cleanup guarantees.

## Repeating the checks

From the repository root, run `./test.sh` for all automated checks or `./test.sh "duplicate"` for that subset. Run `./build.sh` for the optimized app and zip. The README documents the window snapshot and isolated developer-cleanup entry points.
